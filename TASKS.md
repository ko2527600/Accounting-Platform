- [x] Cash Flow Statement (indirect method) (2026-07-31) - closes item 4 from the Ghana market research roadmap's Candidate System Features list. `Account` gained a real `isCashEquivalent` flag (auto-defaulted by name, overridable) so Operating/Financing activities can be computed from real ledger balance changes; `netCashFromOperating + netCashFromFinancing` is verified to always reconcile with the actual cash account balance change (`cashTies`), by the same double-entry guarantee the Balance Sheet's `isBalanced` relies on. No Investing section - documented simplification, this schema has no fixed-asset/loan classification to separate it from ordinary working capital. New page at `/reports/cash-flow` with the same PDF/Word/CSV export the other reports have. See STATUS.md.
- [x] Credit Notes (AR) and Debit Notes (AP) (2026-07-31) - closes item 6 from the Ghana market research roadmap's Candidate System Features list. Since this platform recognizes revenue/expense only at payment time (no separate AR/AP ledger posting at invoice/bill creation), a note against an unpaid invoice/bill simply reduces what will be charged on payment (no journal entry), while a note against an already-paid one posts a real reversing entry and leaves the original payment record untouched - `method` on each note records which path was taken explicitly. Financial correction only - does not adjust inventory stock for returned goods, a distinct concern left out of scope. New "Credit Note"/"Debit Note" action on `Invoices.tsx`/`VendorBills.tsx`. See STATUS.md.
- [x] KPI & Financial Ratio Dashboard (2026-07-31) - closes item 11 from the Ghana market research roadmap's Candidate System Features list. New `/reports/kpis` page: Net Profit Margin, Return on Assets, Equity Ratio, Debt-to-Equity, and Cash Ratio (the last reusing the `isCashEquivalent` flag built for the Cash Flow Statement) - computed entirely from existing Balance Sheet/P&L data. Deliberately excludes Gross Margin/Inventory Turnover (no COGS tracked anywhere - POS sales never post a COGS entry) and Current/Quick Ratio (no current-vs-non-current account classification exists), rather than showing a fabricated approximation. See STATUS.md.
- [x] Layered Ghana Tax Levy Breakdown (2026-08-01) - closes item 2 from the Ghana market research roadmap's Candidate System Features list, following the 2026-08-01 primary-source verification against `gra.gov.gh` (flat 20% = 15% VAT + 2.5% NHIL + 2.5% GETFund Levy). `TaxRate` gained an optional `components` breakdown (validated to sum to the rate's own total); a "Use Ghana VAT Preset" button pre-fills the real split. Invoices snapshot the resolved per-levy amounts into `Invoice.taxBreakdown` at creation time so later edits to a tax rate's components never rewrite past invoice history. See STATUS.md.
- [x] Implement tenant-specific data isolation logic across all services (w:10)
- [x] Set up CI/CD pipeline for automated deployments (w:7) - `.github/workflows/ci.yml` added 2026-07-25: backend job (typecheck, migrate, full Jest suite against real Postgres/Redis service containers) and frontend job (lint, typecheck+build).
- [x] Conduct initial security audit and hardening (2026-07-27) - a real audit (not just a pentest checklist) found and fixed a genuine backdoor (hardcoded `smsCode: "1234"` phone-verification bypass, worked for any account in any environment) and a hardcoded third-party SMS gateway credential, plus added token revocation/logout (JWTs previously had no server-side kill switch at all), a real server-side password policy (was `length < 6`), timing-safe admin-passcode comparison, HTML-escaping in outbound emails, opt-in `trust proxy` support, and an explicit restrictive CSP. See STATUS.md for the full writeup. **Still open, explicitly deferred with reasoning**: no schema validation library (zod/joi) across routes - large mechanical effort, not a critical vuln since Prisma's parameterized queries already prevent real SQL injection (confirmed via full raw-SQL audit); `react-router`/`react-router-dom`'s known high-severity advisory needs a breaking major-version bump - its own scoped upgrade; a full third-party penetration test has still not been performed.

## Known Issues

- [x] **Point of Sale frontend is now real** (2026-07-27) - closes the gap found the same day. New `/pos` page (`PointOfSale.tsx`, linked from the Sidebar) opens a till, records real cash sales against the existing `/tills/*` backend (deducts stock, computes change, generates a receipt), and closes with a live Balanced/Over/Short reconciliation. A real string-vs-number comparison bug in the closeout display (Prisma `Decimal` serializes as a string) was found and fixed during live browser verification. See STATUS.md. **Still separately true**: `Invoices` still never touches inventory - paying an invoice does not deduct stock; that remains a distinct, intentional AR-only flow, not a gap in this change.
- [x] **POS now supports a real multi-item cart** (2026-07-28) - closes a real gap a user hit directly: recording a sale for a customer buying several items required one full "sale" transaction per item (no search, no cart - `POST /tills/sales` only ever accepted one `itemId`/`quantity`, with no line-items concept in the schema at all). Added a `CashSaleLine` table, rewrote the sales endpoint to accept `items: [{itemId, quantity}]` and process the whole basket atomically (one receipt, one combined total/change, all-or-nothing stock deduction), and rebuilt the POS sale form around a real search-to-add basket. See STATUS.md.
- [x] **Location/warehouse-scoped permissions are now real** (2026-07-27) - closes the gap found the same day. `User.role` is now validated against a closed set (`Admin`, `Accountant`, `Auditor`, `Viewer`, `Shop Manager`, `Cashier`) at invite time; `Shop Manager`/`Cashier` require at least one assigned warehouse and are enforced (via a new `WarehouseAccess` join table + `assertWarehouseAccess()`) across Inventory, Warehouses, and Cash Till - blocked with a clear 403 outside their assigned shop(s). An admin can reassign a member's shops anytime via `PUT /tenants/members/:id/warehouse-access`. Design based on deep research into Square/Lightspeed/Shopify POS/QuickBooks/Zoho/Odoo/TallyPrime's permission models. See STATUS.md. **Known scope boundary**: this covers Inventory/Warehouses/Till only - the Dashboard's company-wide financial totals are unaffected since `JournalEntry`/`Ledger`/`Account` have no warehouse concept in this schema at all.
- [x] `POST /api/v1/banking/connect` no longer returns hardcoded demo transactions - real Mono Connect integration built 2026-07-25 (`monoService.ts`, real Connect Widget in `BankReconciliation.tsx`, real webhook + manual sync). **Still needs real credentials to actually work**: `MONO_SECRET_KEY`, `MONO_WEBHOOK_SECRET` (backend `.env`), and `VITE_MONO_PUBLIC_KEY` (frontend `.env`) - sign up at https://app.mono.co. Until then, `POST /connect` returns a clear 503 "not configured" and the frontend shows a disabled-button notice, rather than silently faking a connection.
- [x] Scheduled Reports are now fully real (2026-07-25): a real `ReportSchedule` table persists each tenant's frequency/recipients/enabled state across restarts, and an hourly dispatcher (`ScheduledEmailCronService.runDueSchedulesJob`) actually sends based on it - replacing both the in-memory `POST/GET /schedule` endpoints and the previous hardcoded-every-Monday cron, which (newly discovered) had also been sending fake hardcoded figures to every tenant unconditionally. Tenants must explicitly enable a schedule to receive it (a deliberate behavior change, chosen over silently keeping every tenant's implicit send-by-default). The Settings UI's enable toggle, previously dead React state with no control bound to it, is now wired to actually persist.

Confirmed fixed by running the full backend suite twice consecutively without flushing Redis between runs (previously reproducibly flaky on the second pass). See STATUS.md.

- [x] **Outbound email migrated from Gmail SMTP → Resend → SendGrid (Single Sender Verification)** (2026-07-29) - direct SMTP to Gmail never worked from Render: first an IPv6 routing bug (`ENETUNREACH`, fixed), then confirmed outbound SMTP is blocked entirely on both port 465 and 587 (`ETIMEDOUT` on each), so email moved to Resend's HTTPS API. Once `RESEND_API_KEY` was actually set in production, live logs showed a further real block: Resend's sandbox mode refuses delivery to anyone but the account's own registered email until a domain is verified, and the user doesn't own a domain yet. Migrated again to **SendGrid**, using **Single Sender Verification** (verify one individual email address instead of an entire domain - no domain purchase needed) so real users can actually receive mail today. **Still needs real credentials**: sign up at sendgrid.com, verify a Single Sender email under Sender Authentication, generate an API key, then set `SENDGRID_API_KEY` + `EMAIL_FROM` (must exactly match the verified sender) in Render. **Known tradeoff**: single-sender deliverability is weaker than a verified domain (more spam-folder risk) - migrate to full domain authentication once a domain is available. See STATUS.md.
