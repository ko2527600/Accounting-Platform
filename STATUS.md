## [Date: 2026-07-25] - Fixed Critical Cross-Tenant Data Leak (Invoices, Banking, Inventory, Cash Till, Notifications, Custom Fields)

**What:** Fixed the critical tenant-isolation bug flagged (unfixed) in the previous entry - every tenant on the platform was reading and writing the exact same rows for Invoicing, Vendor Bills, Banking, Inventory/Warehouses, Cash Till, Notifications, Customers, Vendors, and Custom Fields.
1. **First attempt (reverted): per-tenant schema.** Initially tried moving these tables into each tenant's own Postgres schema (matching Account/JournalEntry/Ledger) via a new `tenantMigrations.ts` version. This failed: Prisma Client's typed queries (`client.invoice.findMany()`) always schema-qualify to whatever schema is in `DATABASE_URL` (`public`), completely ignoring the runtime `SET LOCAL search_path` trick that `withCurrentTenantDb` relies on - that trick only works for the raw-SQL repositories (`accountRepository.ts` etc.), not Prisma-model-based routes. Confirmed by testing against a DB with the tables only in tenant schemas: every route errored with "table does not exist" since Prisma kept querying `public.*`. Reverted both the new migration and the `public` table drop.
2. **Correct fix: `tenantId` column + explicit filtering.** Added a `tenantId` column (with index) to all 18 affected models - `BankAccount`, `BankTransaction`, `Customer`, `Invoice`, `InvoiceItem`, `Vendor`, `VendorBill`, `Warehouse`, `InventoryItem`, `WarehouseStock`, `StockTransfer`, `StockTransferItem`, `CashTill`, `CashSale`, `DailyCloseoutReport`, `Notification`, `CustomField`, `CustomFieldValue` - matching the pattern `Invitation`/`User` already used correctly. Converted global-uniqueness constraints (invoice/bill/transfer/receipt numbers, warehouse codes, SKUs, custom field names) to be scoped per-tenant, since the old global uniqueness was itself an artifact of the shared-table bug (no reason Tenant A and Tenant B shouldn't both be able to use warehouse code "WH-001"). Updated every route in `invoices.ts`, `bills.ts`, `banking.ts`, `inventory.ts`, `cashTill.ts`, `notifications.ts`, `analytics.ts`, and `customFields.ts` to filter/set `tenantId` via `requireTenantContext()`, and to verify that any referenced foreign entity (customer, vendor, warehouse, item) actually belongs to the caller's tenant before linking it (closing an IDOR path, not just a listing leak).
3. **Custom Fields now actually persist**, closing out the previous entry's blocked item: `POST /api/v1/custom-fields` was a mock response with a `Math.random()` ID that never touched the database; it's now a real, tenant-scoped `CustomField` row with duplicate-name detection (409) and field-type validation.
**Why:** This was the highest-severity finding possible for a multi-tenant platform - every business using the platform could read and act on every other business's invoices, customers, warehouses, and notifications. Fixed as a straight bug fix (not a data-migration project) since this environment has no real production data in these tables yet.
**Verification:** Live cross-tenant reproduction before and after the fix: onboarded two tenants, had Tenant A create a "SECRET" customer/invoice/warehouse/notification, confirmed Tenant B's list endpoints returned them (bug) and then returned empty (fixed) - repeated end-to-end with the backend actually running, not just via the test suite. Added a permanent regression test (`businessTablesTenantIsolation.test.ts`) covering both the listing leak and an IDOR check (Tenant B cannot `/pay` Tenant A's invoice by guessing its ID - gets 404). Full backend suite: 187/188 passing; the one remaining failure is the same pre-existing, unrelated stale mock in `accountingSchema.test.ts` documented previously.
**Files Affected:** `backend/prisma/schema.prisma`, `backend/prisma/migrations/20260725031500_add_tenant_id_to_business_tables/`, `backend/src/routes/invoices.ts`, `backend/src/routes/bills.ts`, `backend/src/routes/banking.ts`, `backend/src/routes/inventory.ts`, `backend/src/routes/cashTill.ts`, `backend/src/routes/notifications.ts`, `backend/src/routes/analytics.ts`, `backend/src/routes/customFields.ts`, `backend/src/tests/businessTablesTenantIsolation.test.ts` (new), `STATUS.md`, `TASKS.md`.

## [Date: 2026-07-25] - System-Wide Gap Audit: Missing Migrations, Security Fixes, Race Conditions

**What:** Following a system-wide audit (backend routes, frontend wiring, ops/security/process - see prior entry for the audit that found these), fixed the highest-severity findings:
1. **Missing Prisma Migrations (16 models + 4 columns):** `schema.prisma` defines 33 models but the tracked migration files only created 17 - `Invitation`, `BankAccount`, `BankTransaction`, `Customer`, `Invoice`, `InvoiceItem`, `Vendor`, `VendorBill`, `Warehouse`, `InventoryItem`, `WarehouseStock`, `StockTransfer`, `StockTransferItem`, `CashTill`, `CashSale`, `DailyCloseoutReport`, `Notification`, plus 4 more `User` columns (`is_email_verified`, `is_phone_verified`, `email_verification_token`, `sms_verification_code`) had no migration at all - meaning Invoicing, Banking, Inventory, and Notifications were entirely unusable on a fresh `prisma migrate deploy`. Generated a real tracked migration (`20260725020528_add_missing_production_tables_and_audit_log_columns`) via `prisma migrate diff` against a migrations-only DB, and verified a completely fresh database now deploys with zero drift.
2. **Hardcoded secret fallbacks removed:** `jwt.ts` and `broadcastService.ts` fell back to hardcoded default secrets when `JWT_SECRET`/`BROADCAST_MASTER_SECRET` were unset, letting anyone who reads the source forge tokens/bypass the broadcast passcode. Both now throw at startup instead. Documented both as required in `.env.example`.
3. **Unauthenticated admin endpoint:** `POST /api/v1/admin/migrations/run` had zero auth middleware. Added `authenticateJwt` + `requireRole('Admin')`.
4. **Cross-user notification bug:** `PUT /notifications/read-all` had no `userId` filter and marked every tenant notification as read, not just the caller's. Added the same visibility filter (`own or global`) used by the `GET` endpoint.
5. **Race conditions in stock transfers and cash till sales:** both did read-then-compute-then-write on `quantityOnHand`/`cashSalesTotal`, so two concurrent requests could both read the same stale value - proven via a concurrency test to cause a lost-update bug that silently creates phantom stock (both destinations receive the full transferred quantity while the source is only debited once). Fixed with atomic guarded `updateMany`/`increment`/`upsert` operations.
6. **Invoice/bill numbering collisions:** `invoices.ts`/`bills.ts` generated numbers via `count()+offset`, guaranteed to collide under concurrent creation (proven via test, causing a 500 from the unique constraint). Switched to the `${PREFIX}-${Date.now()}-${random}` pattern already used for journal entry numbers.
7. **Dead route discovered mid-fix:** `auth.ts` registered `POST /verify` twice - once for email/SMS account verification (the one the frontend actually uses) and once for JWT header verification (used only by `auth.test.ts`, but Express always dispatches to the first match, so this second handler was completely unreachable). Renamed the JWT-check handler to `POST /verify-token`.
**Why:** These were found via a prior read-only audit (3 parallel agents covering backend, frontend, and ops/security) that traced the same "shipped without ever running against a real database" pattern already found in the ledger-posting bug from the previous session. Several of the audit's other findings (fake bank feed integration, non-persisting custom fields, in-memory-only scheduled reports, cosmetic multi-currency, hardcoded admin diagnostics, orphaned DB tables with no API) were left unfixed and logged in `TASKS.md` under Known Issues, since they need a product decision (build for real vs. relabel/hide) rather than a bug fix.
**Verification:** For every fix, wrote a real integration test against a live PostgreSQL database (no mocks) that fails against the pre-fix code and passes against the fix - each was manually confirmed both ways by temporarily reverting the fix and re-running. Full backend test suite: 167/173 passing, with the remaining 6 failures confirmed to be pre-existing and unrelated (a stale mock in `accountingSchema.test.ts` for pre-refactor `postJournalEntryToLedger`, an existing `/ledgers` pagination shape mismatch, a TS-compile-broken `performanceAndHardening.test.ts`, and two tests that don't account for the verified-registration login gate - all logged in Known Issues, none introduced by this session).

## [Date: 2026-07-25] - Fixed Broken Ledger Posting & Frontend Balance/Currency Bugs (Chart of Accounts, General Ledger)

**What:** Audited the Chart of Accounts, Journal Entry, and Ledger frontend UI (introduced silently in the `dcb13ed` commit without a `STATUS.md`/`TASKS.md` update) and fixed four bugs found during verification against a live PostgreSQL database:
1. **Critical Backend Bug - Ledger Posting Always Failed:** `postJournalEntryToLedger` in `ledgerRepository.ts` ran `SELECT DISTINCT ON (account_id) ... FOR UPDATE`, which PostgreSQL rejects (`FOR UPDATE is not allowed with DISTINCT clause`, code `0A000`). This meant **no journal entry could ever be posted to the ledger** in a real database. Fixed by moving the row lock into an inner subquery and applying `DISTINCT ON` in the (lock-free) outer query.
2. **Frontend Bug - General Ledger Page Crashed:** `useLedgerReport.ts` destructured the ledger statement response using a flat shape (`{account, transactions, closingBalance, totalDebits, totalCredits}`) that never matched the backend's actual nested response (`{account, statement: {transactions, openingBalance, totalDebit, totalCredit, closingBalance}}`). `transactions` was always `undefined`, so `transactions.map(...)` threw as soon as any account was selected. Fixed the destructuring, corrected field names, and used `runningBalance` (not the raw ledger row `balance`) for the running balance column.
3. **Frontend Bug - Chart of Accounts Balance Always $0.00:** `useAccounts.ts` hardcoded `balance: 0` for every account instead of fetching real data. Fixed by calling the existing bulk `GET /ledgers/summary` endpoint (single query, no N+1) alongside `GET /accounts` and merging each account's real `closingBalance`.
4. **Frontend Bug - Hardcoded USD Currency:** `ChartOfAccounts.tsx` and `GeneralLedger.tsx` formatted every balance as USD regardless of the account's actual `currency` field returned by the backend. Added `currency` to the frontend `Account` type and used each account's real currency for formatting.
**Why:** These bugs meant the Chart of Accounts, Journal Entry, and Ledger UI — despite existing in the codebase and being routed in `App.tsx` — were non-functional end-to-end: journal entries could never be posted, and even if they could, the General Ledger page would crash and account balances would always read $0.00.
**Verification:** Stood up a real PostgreSQL 16 instance, ran Prisma migrations, onboarded a live tenant via `POST /api/v1/tenants/onboard`, created two real accounts (one USD, one EUR), posted a real journal entry through `POST /api/v1/journal-entries` + `/post`, and confirmed via Playwright screenshots against the running frontend (`localhost:5173`) that Chart of Accounts shows the correct per-account balance and currency, and General Ledger shows correct opening/closing balances and transaction history with no crash. Also ran `backend/src/tests/ledgers.test.ts` and `journalEntries.test.ts`: before the fix, journal posting failed in test setup (cascading 14 skipped tests); after the fix, 34/36 pass. The remaining 2 failures are a pre-existing, unrelated pagination response-shape mismatch in `GET /api/v1/ledgers` (test expects `data.pagination.page`, API returns `data.page` flat) that predates this change and was not introduced by it — left undone as out of scope.
**Files Affected:** `backend/src/repository/ledgerRepository.ts`, `frontend/src/hooks/useAccounts.ts`, `frontend/src/hooks/useLedgerReport.ts`, `frontend/src/pages/accounts/ChartOfAccounts.tsx`, `frontend/src/pages/reports/GeneralLedger.tsx`, `frontend/src/types/accounting.ts`, `STATUS.md`, `TASKS.md`.
