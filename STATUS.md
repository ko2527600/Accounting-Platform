## [Date: 2026-07-25] - Phase 1 of New-Modules Plan: Real Tax Rates (Replaces Hardcoded 10% Invoice Tax)

**What:** `backend/src/routes/invoices.ts` hardcoded `const tax = subtotal * 0.10;` for every invoice, regardless of tenant, jurisdiction, or customer - the `tax_rates` DB table existed in the schema but had zero API surface (a documented Known Issue). Built the first of four planned new modules on top of the Phase 0 `tenantId` foundation:
1. **Full CRUD** (`backend/src/repository/taxRateRepository.ts`, `services/taxRateService.ts`, `routes/taxRates.ts`, mounted at `/api/v1/tax-rates`) - tenant-scoped, following the established `ReportSchedule`-style shared-table pattern (plain Prisma calls filtered by `tenantId`, not `withCurrentTenantDb`). Rate validated to be a sane fraction (0, 1]; codes are unique per tenant (`@@unique([tenantId, code])`); deleting a rate that's referenced by any invoice is blocked (must deactivate instead).
2. **Real tax resolution on invoice creation**: `Invoice` gets a new `taxRateId` (nullable FK, `onDelete: SetNull`, matching the `customerId`/`Customer` relation pattern already on the model). Creating an invoice now either uses an explicitly-passed `taxRateId`, or resolves the tenant's single active rate covering the invoice date (`effectiveFrom <= date <= effectiveTo ?? now`) - if the tenant has zero active rates, tax is honestly `0`, not a guessed percentage; if more than one active rate covers the date, the request is rejected (400) rather than silently picking one, forcing an explicit choice.
3. **Frontend**: new `frontend/src/pages/settings/TaxRates.tsx` (list + create + delete, linked from the sidebar's Finance & Banking group) and a tax-rate selector added to the invoice-creation modal in `Invoices.tsx` (defaults to "use the active rate" if left unselected).
**Verification:** New `backend/src/tests/taxRates.test.ts` (6 tests): CRUD validation, per-tenant code uniqueness (same code in two different tenants is fine), cross-tenant isolation (a tenant can't fetch another's rate), the real invoice-tax-calculation integration (a 15% rate produces real 15% tax, not the old flat 10%), the multiple-active-rates-requires-explicit-choice guard, and the delete-blocked-while-in-use guard. Full backend suite: 213/213 passing, twice in a row. Frontend `tsc -b` clean.
**Files Affected:** `backend/prisma/schema.prisma`, `backend/prisma/migrations/20260725071000_add_tax_rate_id_to_invoices/` (new), `backend/src/repository/taxRateRepository.ts` (new), `backend/src/services/taxRateService.ts` (new), `backend/src/routes/taxRates.ts` (new), `backend/src/routes/invoices.ts`, `backend/src/app.ts`, `backend/src/tests/taxRates.test.ts` (new), `frontend/src/pages/settings/TaxRates.tsx` (new), `frontend/src/pages/invoices/Invoices.tsx`, `frontend/src/App.tsx`, `frontend/src/components/layout/Sidebar.tsx`, `STATUS.md`, `TASKS.md`.

## [Date: 2026-07-25] - Phase 0 of New-Modules Plan: Added `tenantId` to the 6 Orphaned Tables

**What:** Kicking off a larger, user-approved multi-phase plan to build real functionality for `tax_rates`, `fiscal_periods`, `budgets`, `recurring_transactions`, `approval_workflows`, and `approval_steps` (all previously DB tables with zero API surface - see TASKS.md Known Issues), plus real multi-currency conversion and a platform-wide audit log view. Investigation found none of these 6 tables had a `tenantId` column at all, unlike every other shared business-data table in the schema - this had to be fixed first since it's the foundation every subsequent phase depends on.
**Fix:** Added `tenantId String @map("tenant_id")` + `@@index([tenantId])` to all 6 models, matching the established bare-column (no `@relation`) shared-table pattern used by `BankAccount`/`Customer`/etc. Also fixed two related global-uniqueness bugs discovered while doing this - `TaxRate.code` was declared `@unique` (globally, across all tenants) and `FiscalPeriod` had `@@unique([fiscalYear, periodNumber])` (also global) - both would have silently prevented two different tenants from ever using the same tax code or having a "Period 1 of fiscal year 2026," which is obviously wrong for a multi-tenant system. Changed both to tenant-scoped composite uniques (`@@unique([tenantId, code])` / `@@unique([tenantId, fiscalYear, periodNumber])`). Confirmed all 6 tables were completely empty (zero rows, nothing has ever used them) before adding the columns as `NOT NULL` directly, no backfill/default needed.
**Verification:** Full backend suite: 207/207 passing. `tsc --noEmit` clean.
**Files Affected:** `backend/prisma/schema.prisma`, `backend/prisma/migrations/20260725070000_add_tenant_id_to_orphaned_tables/` (new), `STATUS.md`.

## [Date: 2026-07-25] - Fixed the 5 Pre-Existing Backend Test Failures (Ledger Posting Mock + Mono Banking Test Isolation)

**What:** Investigated the 5 test failures flagged as a Known Issue while fixing the Quick Start Guide PDF. Both were confirmed real but non-production bugs via targeted investigation (one via `git stash` diffing against the base commit, the other via a live Postgres run capturing the actual thrown error):
1. **`accountingSchema.test.ts` ledger-posting failure - a stale test mock, not a code bug.** `postJournalEntryToLedger` (`ledgerRepository.ts`) was correctly refactored in an earlier commit to replace a per-line balance-fetch query with one batched query before the insert loop (a legitimate deadlock/correctness fix). The test's hand-written `mockResolvedValueOnce` chain was never updated to match - it still stubbed 6 sequential responses assuming the old alternating "fetch-balance, insert" pattern, but the real code now only makes 5 calls. Jest's mock queue is consumed strictly in call order, so the second ledger line's INSERT silently consumed the wrong stub (`[]`), making `mapLedgerRow` crash on an undefined row.
2. **`banking.test.ts` Mono `/connect` 500 - real orphaned test data, confirmed via a live run (not a schema-drift or axios-mock issue - both concretely ruled out).** `BankAccount.monoAccountId` is a *globally* unique column, but the test used hardcoded literal Mono account ids (`'mono-acc-tenant1'`, etc.) instead of scoping them to the run like the tenant slugs already do. A previous run's rows survived because `BankAccount`/`BankTransaction` live in the shared `public` schema with no FK/cascade back to `Tenant`, and the test's cleanup never deleted them - so the next run's `POST /connect` hit a genuine Prisma `P2002` unique-constraint collision against leftover rows from an earlier run, surfacing as a 500 and cascading into 3 more failures that read `.bankAccount.id` off the failed response.
**Fix:**
1. `accountingSchema.test.ts`: collapsed the two now-nonexistent per-line balance-fetch mocks into a single stub representing the real batched query, matching the actual 5-call sequence. No production code changed - `ledgerRepository.ts` was already correct.
2. `banking.test.ts`: scoped every literal Mono account id to the test run (reusing the existing `runId` already used for tenant slugs), and extended `cleanupTestData()` to explicitly delete `BankAccount` rows for the test's own tenant ids (captured from `onboardTenant`'s real response) before/after the suite, so leftover bank data can no longer survive between runs.
3. **Deliberately did not** add a `Tenant` → `BankAccount` FK/cascade relation, despite that being one option surfaced during investigation: every other tenant-scoped shared table in `schema.prisma` (~20 models - `Customer`, invoices, etc.) deliberately uses the same bare `tenantId` column-filtering pattern with no FK, and there is no tenant-deletion endpoint in production today (per the existing Known Issues list) for a cascade to matter yet. Adding a one-off FK just to `BankAccount` would have been an inconsistent, unrequested schema change for a gap that's currently test-only; the test-level fixes above fully resolve the actual failures without touching production schema.
**Verification:** Full backend suite run twice in a row against real Postgres/Redis: 207/207 passing both times (up from 202/207). `tsc --noEmit` clean. (One transient run mid-verification showed 3 unrelated failures in `performanceAndHardening.test.ts` after the sandbox's Redis process died outside of any test - restarting Redis and rerunning confirmed this was sandbox instability, not a real regression; it did not recur.)
**Files Affected:** `backend/src/tests/accountingSchema.test.ts`, `backend/src/tests/banking.test.ts`, `STATUS.md`, `TASKS.md`.

## [Date: 2026-07-25] - Fixed Rate Limiter Key Collision Between api/auth/onboarding Limiters

**What:** `apiRateLimiter`, `authRateLimiter`, and `onboardingRateLimiter` (`backend/src/middleware/rateLimiterMiddleware.ts`) all built their Redis counter key identically - `rate_limit:${tenantOrIp}` - with no way to tell which limiter incremented it. Since `apiRateLimiter` is mounted globally on every `/api/` route, ordinary traffic (e.g. a single page load firing several parallel GETs) inflated the exact same counter the much stricter `authRateLimiter` (10/min) and `onboardingRateLimiter` (5/min) check against. A real user's first login-then-save on a data-heavy page (confirmed live: the new Scheduled Reports Settings tab) could get spuriously 429'd by their own unrelated page-load traffic, with the error surfacing as a confusing "Too Many Requests" on an action that made only one or two actual calls to the limited route.
**Fix:** Added a required `name` field to each limiter's options (`'api'`/`'auth'`/`'onboarding'`) and namespaced the cache key by it: `rate_limit:${name}:${tenantOrIp}`. Each limiter now has its own isolated budget per tenant/IP, as originally intended.
**Verification:** New `rateLimiterKeyIsolation.test.ts` - fires 15 requests through `apiRateLimiter` for a tenant (over `authRateLimiter`'s 10/min limit, under `apiRateLimiter`'s own 100/min), then confirms a single `authRateLimiter` check for the same tenant still passes. Confirmed the test **fails** against the pre-fix shared-key code (auth check blocked at count 16) and passes after the fix - the rate limiter module bypasses itself under `NODE_ENV=test`, so the test temporarily flips it to exercise the real Redis-backed path. Full backend suite: 201/202 (same pre-existing unrelated stale-mock flake documented in every prior entry this session). Reproduced and confirmed fixed live: the exact "Settings page save gets 429'd" scenario found while verifying the Scheduled Reports feature no longer occurs after this fix.
**Files Affected:** `backend/src/middleware/rateLimiterMiddleware.ts`, `backend/src/tests/rateLimiterKeyIsolation.test.ts` (new), `STATUS.md`, `TASKS.md`.
