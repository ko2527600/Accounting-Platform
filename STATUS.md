## [Date: 2026-08-02] - Fix Monthly Executive Reports (Never Fired) + Add Period-over-Period Deltas to Weekly/Monthly Emails

**What:** User asked to update the weekly and monthly executive email reports sent to tenant companies, and to add a decision document. Investigation (see `docs/decisions/0001-weekly-monthly-executive-email-reports.md`) found `ReportSchedule.frequency` was persisted from Settings but never actually read by the cron dispatcher: `ScheduledEmailCronService.runDueSchedulesJob()` only ever checked `dayOfWeek`/`hourUtc`, so a tenant who picked "Monthly" silently kept getting weekly sends (or, depending on `dayOfWeek`, potentially none) - monthly delivery was effectively a no-op. The Settings UI made this worse: the frequency field was a disabled input hardcoded to `"Weekly (Every Monday at 8:00 AM)"`, so there was no way to actually select Monthly even if the backend had honored it. Separately, the email template itself was three flat numbers with no trend context (up vs. down vs. last period).

**Fix:** Added a `dayOfMonth` column to `ReportSchedule` (migration `20260802063000_add_day_of_month_to_report_schedules`, default `1`). `scheduledEmailService.ts` now has a shared `computePeriodReportData(tenantId, periodStart, now)` helper used by both `computeWeeklyReportData` (trailing 7 days) and the new `computeMonthlyReportData` (trailing 30 days) - each returns the current period's totals plus `salesChangePercent`/`itemsChangePercent` vs. the immediately preceding period of equal length (`null` when there's no prior data, e.g. a brand-new tenant, instead of a misleading 0%/∞). `runDueSchedulesJob()` now branches on `schedule.frequency`: `Weekly` matches `dayOfWeek`+`hourUtc` with the existing 6-day dedup guard; `Monthly` matches the new `dayOfMonth`+`hourUtc` with a 27-day guard. `EmailService` gained a shared `buildPeriodReportHtml()` template - a 2-column stat-tile grid with color-coded ▲/▼ deltas - plus `sendMonthlyExecutiveReport()` alongside the existing (now delta-aware) `sendWeeklyExecutiveReport()`. `POST /api/v1/reports/schedule` now accepts optional `dayOfWeek`/`dayOfMonth`/`hourUtc` overrides (previously ignored), and `POST /schedule/test-email` reads the tenant's saved `frequency` to preview the correct template instead of always sending the weekly one. Settings UI: the frequency field is now a real Weekly/Monthly `<select>` wired to the existing load/save endpoints, with copy that reflects the selected cadence.

**Verification:** `tsc --noEmit` (backend) and `tsc -b` (frontend) both clean after a fresh `npm ci`/`prisma generate`. Updated `backend/src/tests/scheduledReports.test.ts` and `backend/src/tests/smsAndNodemailerReports.test.ts` for the `weeklySales` → `periodSales` field rename (the shared field name across both cadences) and the two new required delta fields. **Not run**: this sandbox has no reachable PostgreSQL instance (`pg_isready` fails, no `DATABASE_URL` configured), so the integration suite (which spins up real tenants/closeouts against a live DB) could not be executed here - flagging this explicitly rather than claiming a pass. Recommend running `npm test` in an environment with a live test DB before merging.
**Files Affected:** `backend/prisma/schema.prisma`, `backend/prisma/migrations/20260802063000_add_day_of_month_to_report_schedules/migration.sql` (new), `backend/src/services/scheduledEmailService.ts`, `backend/src/services/EmailService.ts`, `backend/src/routes/scheduledReports.ts`, `backend/src/tests/scheduledReports.test.ts`, `backend/src/tests/smsAndNodemailerReports.test.ts`, `frontend/src/pages/settings/Settings.tsx`, `docs/decisions/0001-weekly-monthly-executive-email-reports.md` (new).

## [Date: 2026-07-31] - Remove Team Member Feature + Passcode-Gated "Onboard Contracted Client" Admin Tool

**What:** Follow-up to the previous entry's "Change Role" feature. The user wanted a real way to take a team member off a workspace entirely (freeing their email for reuse), and separately, a way for the platform operator to onboard a business directly - skipping the normal email/SMS verification round-trip - for cases where the business has already been vetted through a signed contract, not a self-serve signup. (This request was originally phrased using the word "backdoor" across several turns; that literal ask was explicitly declined and clarified via `AskUserQuestion` into these two ordinary, auditable, Admin/passcode-gated features instead - no hidden bypass was built.)

**Fix 1 - Remove Team Member:** New `DELETE /api/v1/tenants/members/:id` (`requireRole('Admin')`) in `tenants.ts`. Blocks removing your own account (400, with a clear "have another Admin do it" message) and 404s for a member outside the caller's tenant. Guards against leaving a tenant with zero active Admins: if the target is an Admin, counts other `isActive: true` Admins and blocks the removal (400) if none remain - this guard is only reachable in a narrow edge case (self-removal is already unconditionally blocked earlier), specifically when the caller's own account was deactivated after their JWT was issued but the token is still valid. On success, hard-deletes the `User` row (freeing the email globally, since `User.email` is a platform-wide unique constraint) and writes a `TEAM_MEMBER.REMOVED` audit log entry with the removed member's name/email/role in `details`. Frontend: a "Remove" button (red, `UserMinus` icon) next to "Change Role" on every team member row in `TeamManagement.tsx`, gated behind a `window.confirm()` and wired to a real toast.

**Fix 2 - Onboard Contracted Client:** `onboardTenant()` (`tenantService.ts`) gained a server-side-only `options.skipVerification` parameter - deliberately a function parameter, never read from the request body (`dto`), so it can only be set by trusted internal server code, never smuggled in via a public signup request however it's shaped. When true: the created Admin user gets `isActive`/`isEmailVerified`/`isPhoneVerified` all `true` and no verification tokens, and receives the real welcome-package email immediately (skipping the verification email/SMS entirely). New `POST /api/v1/tenants/admin-onboard`, gated by the existing master-passcode pattern (`BroadcastService.verifyPasscode`, same mechanism as `GET /tenants`) rather than tenant JWT auth - calls `onboardTenant(..., {skipVerification: true})` and writes a `TENANT.ADMIN_ONBOARDED` audit log entry. Frontend: a 5th "Onboard Client" tab in the Admin Core Engine console (`AdminCoreEngine.tsx`), a form for company/admin details, using the already-unlocked session's passcode.

**Verification:** `tsc --noEmit` (backend) and `tsc -b` (frontend) both clean. New `backend/src/tests/teamMemberRemoval.test.ts` (5 tests) and `backend/src/tests/adminOnboard.test.ts` (4 tests, including a dedicated test confirming the public self-serve `/tenants/onboard` endpoint ignores a client-supplied `skipVerification: true` in the request body). Full backend suite run twice in a row: 342/342 passing both times. **Live verification** against real dev servers: onboarded a real tenant, created a second team member directly in the DB, logged into the real UI, clicked "Remove" on that member - confirmed via direct DB query the user row was actually deleted and a `TEAM_MEMBER.REMOVED` audit row was written with the correct actor (`userEmail`/`ipAddress` populated). Separately unlocked the real Admin Core Engine console with the local dev master passcode, filled out and submitted the "Onboard Client" tab - confirmed the success panel rendered, the new admin's DB row was `isActive`/`isEmailVerified`/`isPhoneVerified: true` immediately, a real login against `/auth/login` succeeded with no verification step, and a `TENANT.ADMIN_ONBOARDED` audit row was written. All test tenants/users cleaned up afterward.

## [Date: 2026-07-30] - Add Ability to Change an Existing Team Member's Role

**What:** The user asked to promote an existing team member (already a user in their tenant) to Admin. Investigation found no way to do this anywhere in the app - `POST /tenants/invite` only sets a role once, at invite time, and the only post-invite member-management endpoint that existed was `PUT /members/:id/warehouse-access`. There was no role-change endpoint at all, in the UI or the API - not a hidden/bypassable feature, a genuinely missing one. (Explicitly **not** built as any kind of backdoor or bypass - the request was clarified via `AskUserQuestion` first, and the fix is a normal Admin-gated feature following this session's established RBAC/audit patterns exactly.)

**Fix:** New `PUT /api/v1/tenants/members/:id/role` (`requireRole('Admin')`) in `tenants.ts`, mirroring the existing warehouse-access endpoint's shape: validates the new role against the same `CLOSED_ROLES` list the invite flow uses, 404s if the member isn't in the caller's tenant, no-ops (200) if the role is unchanged, and writes a `TEAM_MEMBER.ROLE_CHANGED` audit log entry with a structured `{role: {from, to}}` diff via the existing `recordAuditLog`/`actorFromRequest` helpers. Added one safety guard with no existing precedent to copy: **blocks demoting a tenant's only remaining active Admin**, to prevent a business accidentally locking itself out of its own Settings/Team Management - counts other `isActive: true` Admins only, since an unverified admin account can't actually log in yet to use that access.

Note surfaced to the user directly (and in the UI's modal copy): role is baked into a user's JWT at login, so a role change takes effect the next time that person logs in, not on their currently active session.

Frontend: new "Change Role" button + modal on every team member row in `TeamManagement.tsx` (Admin-only, same visibility gate as the existing "Manage Access" button), a role `<select>` reusing the same `CLOSED_ROLES` list as the invite modal, wired to the new endpoint with a real toast (success/error) instead of a silent no-feedback save.

**Verification:** `tsc --noEmit` (backend) and `tsc -b` (frontend) both clean. New `backend/src/tests/teamMemberRole.test.ts` (5 tests): non-Admin blocked (403), unrecognized role rejected (400), unknown member 404s, a real role change persists to the DB and writes the correct audit log row, and the last-active-Admin lockout guard is exercised both ways (a demotion that leaves another active Admin succeeds; one that wouldn't is blocked with a clear error). Full backend suite run twice in a row: 333/333 passing both times.
**Files Affected:** `backend/src/routes/tenants.ts`, `frontend/src/pages/team/TeamManagement.tsx`, `backend/src/tests/teamMemberRole.test.ts` (new).

## [Date: 2026-07-30] - Fix PDF Table Cells Wrapping/Overflowing Instead of Truncating

**What:** After PR #35 (real PDF/Word export) merged and Render redeployed, the user downloaded a real Executive Report PDF from production and found the "Code" column wrapped long warehouse codes onto a second line, overflowing the fixed row height and breaking the table's ruled borders. Root cause: `drawSimpleTable()` (`pdfGenerationService.ts`, shared by all 6 generated PDFs - Quick Start Guide, Stock Take Sheet, Balance Sheet, P&L, Executive Report, Stock Intelligence) passed pdfkit's `{ ellipsis: true }` text option without `lineBreak: false`, and pdfkit's automatic single-line ellipsis truncation turned out not to activate in that combination in the installed pdfkit version (0.19.1) - it just wrapped normally instead, silently discarding the width constraint the row height was sized for. A first fix attempt (adding `height`/`lineBreak: false` to the existing `ellipsis: true` option) still reproduced the identical wrapping bug when re-tested - pdfkit's ellipsis logic doesn't reliably respect `lineBreak: false` either.

**Fix:** Replaced reliance on pdfkit's built-in ellipsis with manual measurement: a new `truncateToWidth(doc, text, maxWidth)` helper binary-searches (via `doc.widthOfString()`, using whatever font/size is currently set) for the longest prefix of `text` that fits `maxWidth` alongside a `…` character, and `drawSimpleTable()` now truncates every header/cell string with it before calling `doc.text(..., { lineBreak: false })` - guaranteeing a single line that never overflows regardless of pdfkit's ellipsis quirks. Verified by regenerating the exact PDF from the user's report (`jamco` tenant, the same long `WH-...` warehouse codes) - confirmed the fix actually works this time (`WH-17852…` on one line) after the first attempt had silently failed the same manual check.

Also widened the Stock Take blind-count sheet's SKU column (`0.2` → `0.28` of table width, borrowing from Item Name and Unit) - unlike the Executive Report's "Code" column (a secondary reference field where ellipsis truncation is an acceptable tradeoff), a stock-take sheet's SKU is the primary key someone physically matches against shelf inventory, so truncating it would make the printed sheet unusable. `reportExports.test.ts`'s two PDF-content assertions (`stock-intelligence PDF contains the real seeded SKU`, `closeouts PDF contains the real seeded shop name`) also needed their synthetic test values shortened - they embedded a full millisecond timestamp (`REX-1785419438722`, `Report Export Shop 1785419438722`) which is far longer than realistic production SKUs/shop names and was legitimately triggering the newly-correct truncation, an artifact of the test data rather than a real regression.

**Verification:** `tsc --noEmit` clean. Full backend suite run twice in a row: 328/328 passing both times (including the corrected `reportExports.test.ts`/`stockTake.test.ts` assertions). Manually regenerated the user's exact failing PDF (same tenant name, same long warehouse codes) via a throwaway test script and visually confirmed the fix before/after.
**Files Affected:** `backend/src/services/pdfGenerationService.ts`, `backend/src/tests/reportExports.test.ts`.

**Also confirmed not a bug (user-reported, investigated, found legitimate)**: a downloaded `profit_and_loss_....csv` showing all-zero balances for "Consulting Income"/"Office Rent" is real data - those are the exact account names from `BulkImportWizard.tsx`'s sample Chart-of-Accounts CSV template, meaning the tenant imported the sample template as-is and hasn't posted any real transactions yet. A separately-shared `Stock_Intelligence_Report_....csv` still showing the old fake hardcoded data ("Samsung 24 Inch Monitor" etc.) was downloaded before PR #35 merged and Render redeployed - `GET /analytics/export/csv` returning real data was part of that same already-merged fix, so a fresh download post-redeploy should be correct.

## [Date: 2026-07-30] - Add Contra Voucher (Internal Fund Transfer) (Item #6b on the Ghana Market Research Roadmap)

**What:** Fourth item off the roadmap doc's quick-win list. TallyPrime's "Contra Voucher" concept - an internal transfer between the business's own cash/bank/till accounts (e.g. "till to bank") - was a confirmed real gap: no dedicated entity or UI existed, so recording one required hand-building a manual journal entry with no guardrails.

**Fix:** No schema migration needed - `createJournalEntry` (`journalEntryService.ts`) already accepted a caller-supplied `entryNumber`, so a Contra Voucher is implemented as a constrained wrapper (`createContraVoucher`) that generates its own `CV-` prefixed entry number (vs. the generic `JE-`) as the discriminator, rather than adding a new "type" column. New route `POST /api/v1/journal-entries/contra` (`requireRole('Accountant')`, same as regular journal entry creation).

Frontend: new dedicated `ContraVoucher.tsx` page at `/journals/contra` (a "Transfer Funds" button added next to "Create Entry" on the Journal Entries list) - a constrained form (Date, From/To account dropdowns restricted to Asset-type accounts, Amount, optional Memo) rather than the generic multi-line Journal Builder. Also surfaced `entryNumber` in `JournalList.tsx`'s "Journal ID" column for the first time (it previously always showed the raw UUID, since `useJournals.ts`'s mapper never copied it over) - needed to make the `CV-` discriminator actually visible/searchable in the list, not just present in the database.

**Verification:** `tsc --noEmit` (backend) and `tsc -b` (frontend) both clean. New `describe('8. ## [Date: 2026-07-27] - Fixed CI-Only Tenant Provisioning Failure (Connection-Pool Race in Migration Runner)

**What:** PR #15's CI (`backend` check) failed reproducibly with `Raw query failed. Code: 42804 ... Key columns "journal_entry_id" and "id" are of incompatible types: uuid and text` inside `onboardTenant()`, but the same suite passed 260/260 twice locally. Root-caused to a real, pre-existing connection-pool race in `runMigrationsForSchema` (`backend/src/database/tenantMigrationRunner.ts`): `SET search_path TO "<tenant_schema>", public;` and the subsequent unqualified DDL statements (`CREATE TABLE journal_entries ...`, etc.) were each dispatched as separate, non-transactional `$executeRawUnsafe` calls. `SET search_path` is connection-scoped in Postgres, but Prisma's connection pool is free to route each call to a different pooled connection — under CI's higher concurrency this happened often enough to reliably reproduce, while locally (lower pool contention) it usually didn't. When the DDL statements landed on a connection still on the default `public` search_path, `CREATE TABLE IF NOT EXISTS journal_entries` silently no-op'd against the *pre-existing* Prisma-managed `public.journal_entries` table (whose `id` column is `TEXT`, from `String @id @default(uuid())` with no `@db.Uuid`), so the next statement's `journal_entry_lines.journal_entry_id UUID REFERENCES journal_entries(id)` FK failed with the exact uuid/text mismatch seen in CI. Not introduced by this branch's 3 commits (none touch this file); it's a latent bug that could have hit any tenant onboarding under enough concurrent DB load, in CI or production.
**Fix:** Wrapped the `SET search_path` + tracking-table creation + full migration loop + `SET search_path TO public` reset in a single `prismaClient.$transaction(async (tx) => {...}, { timeout: 30000, maxWait: 10000 })`, which pins every statement to one physical connection for the duration, guaranteeing the search_path actually applies to the DDL that depends on it. Updated the two unit tests that hand-roll a mock Prisma client (`accountingSchema.test.ts`, `tenantMigrationRunner.test.ts`) to mock `$transaction` as `(fn) => fn(mockPrisma)` so existing assertions on `$executeRawUnsafe` calls keep working.
